# Working in this repo

**Shared local config:** `~/.quasar-graph/config.json` stores the user's projects root and clone protocol as `{ "base_dir": "/abs/path", "protocol": "ssh" | "https" }`. The `scan` / `research` / `clone` skills offer `base_dir` as the default when asking for `scan_dir` / `base_dir` and write the confirmed answers back (creating the file if missing, preserving other keys); `clone` persists both keys after its confirmation gate, and `research` reads the saved `protocol` (falling back to `ssh`) for its auto-clone. It sits beside `tokens.json` but is plain preference data, not a credential — the MCP server does not read `config.json`; `base_dir` is passed in as a tool argument. Derived state lives separately under `~/.quasar-graph/cache/` (currently `bindings.json`, owned by the MCP server's `bind_context` tool): everything there is regenerable and safe to delete.

**The skills have no build/lint/test** — they are markdown and execute when invoked from Claude Code. **The MCP server does have tests:** `cd mcp && npm test` (Node's built-in `node --test`; suites under `mcp/test/`, one per transform module). Run it after editing anything under `mcp/src/`. Run a single suite with `node --test test/edges.test.js`; lint with `cd mcp && npm run lint`. GitHub Actions (`.github/workflows/ci.yml`) runs the same `npm run lint` and `npm test` plus `npm audit --audit-level=high` as three parallel jobs (`lint` / `test` / `audit`; Node 20, ubuntu-latest) on pushes to `main` and on pull requests. The server requires **Node ≥ 20** (`mcp/package.json` engines) and is ESM (`"type": "module"`).

**The plugin runs the bundled server, not the sources.** `plugin.json` points at `mcp/dist/index.js` — a committed esbuild bundle (`cd mcp && npm run build`) that inlines all runtime deps so a marketplace install works without `npm install`. After editing `mcp/src/` or `mcp/index.js`, rebuild the bundle or the plugin keeps executing stale code; tests and lint still run against the sources (`dist/` is eslint-ignored).

The server reads `QUASAR_BACKEND_URL` from the env, hardcoded in `plugin.json`'s `mcpServers` `env` block (`https://api.quasar-graph.com`) — deliberately not a `userConfig` field, so installing the plugin never prompts for it; to develop against another backend, temporarily edit the value in `plugin.json` (don't commit that change). `readConfig` (`mcp/src/config.js`) throws if it is unset, so to run the server standalone you must export it first. The plugin is registered for local install via `.claude-plugin/marketplace.json` (`quasar-graph`).

To "test" a skill change:

1. Ensure the repo is symlinked into Claude Code's local-plugins directory so `/quasar-graph:scan` appears.
2. Run `/quasar-graph:scan` against a directory of test projects (no fixtures are committed — use a real projects directory or create disposable ones).
3. Inspect output under `<cwd>/.quasar-graph/<session_id>/` — `manifest.json`, then `scan/projects/<name>/<name>.md` frontmatter, then Phase 3 resource files under `scan/resources/` and `scan/third-party/`.

For resume testing: abort mid-scan, then re-invoke with the same `session_id`. Only `pending` entries should be processed.

# Editing the skills

- **Skills name actions, not tools** (the superpowers portability rule). SKILL.md bodies say "dispatch a sub-agent (general-purpose)", "selection prompt", "load a skill", "edit the file", "run a shell command" — never a harness tool name (`Task`, `AskUserQuestion`, `Edit`, `Bash`, …). The per-harness translation lives in `references/<harness>-tools.md` at the repo root (`claude-code-tools.md` is the mapping for this harness); put harness specifics there, never in skill bodies. Sub-agent dispatch prompts carry the read-`SKILL.md` fallback inline because the sub-agent does not see the orchestrator's context. Only the MCP tool names (`login`, `list_projects`, `plan_clone`, …) stay literal — MCP is harness-agnostic.
- **Shared conventions live in `references/conventions.md`** — the action vocabulary with its degradations (no sub-agent tool → work inline; no skill tool → read the `SKILL.md`; no selection tool → numbered list), the selection-UI rules, the login retry flow, and the repo-URL normalization + bindings-cache shape. Each user-invocable skill points there from its "Conventions" section instead of repeating the text; only what is verbatim-identical across skills belongs in that file. Per-skill specifics stay in the skill bodies: the fixed-choice/gate lists, the terminal outcome when auth ultimately fails (offline offer vs stop), and the `plan_clone` entry filters (`research`: entries containing relevant nodes — clone the missing, ff-only-pull the present, once per session; `context`: only the confirmed neighbor; `clone`: the whole graph) — these differ by design, do not unify them.
- Keep `analyze-project`'s "do NOT invoke directly" warning in its frontmatter description — it's load-bearing to prevent users from triggering it as a top-level command. All three internal skills (`analyze-project`, `research-project`, `install-project`) also carry `user-invocable: false` in their frontmatter, which hides them from the `/` slash menu while keeping them loadable by Task sub-agents via the Skill tool. Do NOT add `disable-model-invocation: true` — that would block the Skill tool and break the orchestrators.
- The analyzer's **file whitelist** (manifests, env, compose, ORM config, root README) is deliberate — do not broaden it to source code. The rule "better to miss than to fabricate" applies to both resources and connections.
- **`connections` are OUTBOUND only** — recorded by the calling side. The analyzer must NOT turn inbound/acceptance config (`CORS_ALLOW_ORIGIN`, `allowed_origins`, nginx `server_name`, Traefik `Host(...)`, webhook allowlists) into a connection, or the graph gets two opposite edges for one relationship. The transform (`mcp/src/transform/edges.js`) dedupes *exact* duplicate edges as a safety net, but cannot fix wrong-direction reciprocals — that contract lives in `analyze-project`, and Phase 3.5's review flags any that slip through.
- **Two edge layers: logical vs ingress.** Logical dependency edges (`connections` + resource `consumers`) are the source of truth and are always emitted. The **ingress overlay** is a separate, additive `routes` edge class: a `kind: gateway` resource carries a `routes:` list of downstream targets (e.g. `traefik → nginx-acme-api → acme-api`), which `edges.js` turns into `gateway → target` edges via `resolveTarget` (project/service name first, then resource slug). Inbound routing config (Traefik `Host(...)`, nginx upstreams) feeds **`routes`**, NOT `connections`. The environment analyzer captures `routes` whenever visible and Phase 3 writes it into the gateway files (always — there is no toggle). The overlay is gateway-downstream only (no synthesized `client → gateway` entry edge) and never replaces a logical edge, so the two layers stay separable by edge `type`.
- When the orchestrator needs to update `manifest.json`, it edits the file itself from the main thread (in Claude Code: the `Edit` tool). Sub-agents must NOT touch `manifest.json` — that contract is what makes resume safe.
- Concurrency = batch of 3 parallel sub-agent dispatches. Increasing it risks rate limits; decreasing it slows scans. Change deliberately.

All documentation, skill bodies, and code comments in this repo are written in **English**.
