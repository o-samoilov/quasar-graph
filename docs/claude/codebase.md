# What this repo is

A **Claude Code plugin** named `quasar-graph`. The scanner itself is markdown skill instructions (no application code); the plugin also bundles a small **Node.js MCP server** under `mcp/` that uploads a completed scan to a backend. The scan produces a session under `.quasar-graph/<session_id>/`: a root `manifest.json` (session control) plus, under `scan/`, per-project markdown, aggregated resource files, and a per-node `manifest.json` carrying graph-owned layout (`{ id, position }`); it then optionally syncs to the backend as nodes/edges.

Manifest: `.claude-plugin/plugin.json`. Skills under `skills/`:

- **`scan`** — entry skill (user-invocable via `/quasar-graph:scan`). Orchestrates the full scan: catalog → deep analysis → aggregate → pre-upload review → upload.
- **`analyze-project`** — internal skill. **Must NOT be invoked directly** — only via sub-agents dispatched by `scan` Phase 2. Its description in the frontmatter says this explicitly.
- **`research`** — user-invocable via `/quasar-graph:research`. Read-only, graph-guided **code search**: binds a backend graph (Phase 0 — if the invocation directory's normalized git remote has an entry in `~/.quasar-graph/cache/bindings.json`, that graph is offered first as the default; the cache lookup is read-only, ownership stays with the `bind_context` MCP tool), then a conversational loop scopes relevant nodes from the graph, rebases `projectPath` onto a local `base_dir`, syncs the **relevant** repos after one confirmation (via `plan_clone`, executing only the entries containing relevant nodes: clones the missing, ff-only-pulls the already-present — at most once per session, skipping dirty working trees), dispatches `research-project` sub-agents (batches of 3) to read source code, and synthesizes a prose answer with `file:line` references. Never writes to the graph or `.quasar-graph/`.
- **`research-project`** — internal skill. **Must NOT be invoked directly** — only via sub-agents dispatched by `research` Phase 1. Searches ONE project's **source code** for a query (the only skill that reads source) and returns structured JSON findings.
- **`clone`** — user-invocable via `/quasar-graph:clone`. Clones (and optionally installs) the projects of a backend graph onto the local machine: binds a graph, calls `plan_clone` to resolve a deterministic clone plan (target paths under a `base_dir`, ssh/https URL, monorepo dedup, clone/pull/skip classification), runs the git commands, then dispatches `install-project` sub-agents (batches of 3) to install dependencies.
- **`install-project`** — internal skill. **Must NOT be invoked directly** — only via sub-agents dispatched by `clone`. Installs dependencies for ONE cloned project, choosing the command (incl. container path) from its config/docs.
- **`context`** — user-invocable via `/quasar-graph:context`. Binds the **current working project** to its graph node by calling the `bind_context` MCP tool with the raw `git remote` URL, the target directory, and `base_dir`; the tool normalizes the URL, looks up and repairs the binding cache (`~/.quasar-graph/cache/bindings.json`, an array of `{ node_name, project_path, project_id, graph_id }` per repo URL because one repo can hold several monorepo nodes and appear in several graphs), falls back to searching every graph, and returns the bound node with its edges and neighbors. The skill loads the node's connections into the session, then for the rest of the session answers structural questions from `edges` and — after one confirmation per neighbor per session — reads dependent projects' code (direct file reads/searches for pinpoint questions, `research-project` sub-agents for deep ones), auto-cloning confirmed missing neighbors via `plan_clone`. Read-only w.r.t. the graph; no offline mode.
- **`edit`** — user-invocable via `/quasar-graph:edit`. Direct graph editing without a scan session: binds a graph (binding-cache default first, else project/graph selection), `pull_graph`s the full snapshot into a fresh session, edits `graph/graph.json` conversationally from the main thread (positions, descriptions, `agentContext`, `links`, adding/removing nodes and edges — placeholder ids allowed, `push_graph` canonicalizes them), then, behind a confirmation gate that summarizes the changes and warns about full-replace semantics, calls `push_graph`. Renames/type changes here keep `position`/`agentContext`/`links` (they travel in the same JSON object). Scan-owned fields may be edited but the next scan refreshes them. No offline mode; never reads source code.

The bundled MCP server (`mcp/index.js`, `mcp/src/`) exposes `login` / `whoami` / `logout` / `list_sessions` / `list_workspaces` / `list_projects` / `create_project` / `list_graphs` / `create_graph` / `get_graph` / `pull_graph` / `write_node_manifests` / `build_graph` / `push_graph` / `plan_clone` / `bind_context`. The backend speaks snake_case on the wire; `mcp/src/backend/wire.js` converts at the client boundary (`getGraph`/`scan`), so the session snapshot (`graph/graph.json`), the transform pipeline, and all tool internals stay camelCase (`repoUrl`, `sourceNodeId`, `data.packageName`), while list endpoints (`list_projects`, `list_graphs`, `list_workspaces`) pass wire JSON through untouched. Every backend project lives in a workspace: `create_project` requires a `workspace_id` and resolves it automatically when the user has exactly one workspace (otherwise it fails listing the options from `list_workspaces`). Skills fetch `list_workspaces` alongside `list_projects` and, when the user has more than one workspace, label each project option with its workspace name (Selection UI rule in `references/conventions.md`). The server authenticates to the backend as the OAuth 2.1 public client `quasar-mcp` (Authorization Code + PKCE with a loopback redirect): `mcp/src/auth/` holds the client — the refresh token persists in `~/.quasar-graph/tokens.json` (0600, keyed by backend URL), the 15-minute access JWT lives only in process memory, `createClient(baseUrl, { auth })` injects `Authorization: Bearer` and retries once after a silent refresh on 401. Refresh tokens rotate on every refresh, so the provider single-flights concurrent refreshes. Interactive login happens only through the `login` tool (opens the browser; on failure returns `status: pending` + `authorize_url` and completes in the background); every other tool fails with `Not authenticated with the quasar-graph backend. Run the "login" tool, then retry.` until login succeeds. `whoami` reports the current session (`logged_in`, `user_id`, `email`, token expiry) via a silent refresh + `GET /oauth/userinfo`; `logout` best-effort revokes the refresh-token family via `POST /oauth/revoke` and always deletes the local credentials. An auth failure is not the offline case — offline mode is only for a missing MCP server. It talks to the backend at `${QUASAR_BACKEND_URL}/api/v1/*` (`/projects`, `/graphs`, `/graphs/:id`, `/scan`) via `mcp/src/backend/client.js`. The scan binds to a backend project + graph **up front** (Phase 0): `list_graphs` accepts an optional `project_id` (sent as `?project_id=`), `create_graph` makes a new empty graph, and `pull_graph` downloads an existing graph into the session writing only `graph/graph.json` (the full snapshot). At the tail of Phase 3, `write_node_manifests` reads `graph/graph.json` + the `scan/` folders and writes a per-node `manifest.json` (`{ id, position, agentContext }`) beside each `.md`, so graph-owned fields are visible and editable before upload. `build_graph` then takes just `session_dir` — it reads `graph_id` from `manifest.backend`, transforms the session into nodes/edges with **deterministic UUIDv5** ids (`mcp/src/transform/`; initial node `position`s and edge anchors come from a left-to-right dagre auto-layout in `mcp/src/transform/layout.js`), overlays graph-owned per-node fields (`position`, `agentContext` — a per-node CLAUDE.md-style instruction blob) from per-folder `scan/.../manifest.json` (folder wins) over the previous `graph/graph.json` snapshot, backfills scan-owned node fields the fresh scan could not produce (`description`, `repoUrl`, `projectPath`, `data` keys, `links` merged by URL) from that same previous snapshot (fill-missing — a fresh value always wins, previous values only patch holes; reported as `backfilled` in the result), and **overwrites `graph/graph.json`** with the assembled snapshot; the actual upload is `push_graph`, the single upload path for both scan and edit. `push_graph` uploads any `graph/graph.json` snapshot — assembled by `build_graph` or pulled and edited (`session_dir`), validates it (non-empty `name`/`type`, no duplicate `(type, name)`, no dangling or self-loop edges — all errors reported together, nothing partial), recomputes node ids (UUIDv5) and edge ids/anchors, rewires edges from in-file ids (placeholders allowed), and POSTs the same full-replace payload to `/scan`. A resource's `admin_url` is surfaced as a **link on the resource node** (`links: [{ name: 'Admin Panel', url }]` in `mcp/src/transform/nodes.js`), not as a separate `admin_panel` node — the management UI is the same component, so it does not get its own node or `manages` edge; an `admin_panel` node exists only for a **scanned project** that declares `role: admin_panel` (a standalone back-office app). Project nodes also carry scan-owned `projectPath` and `repoUrl` (git remote), both captured into the manifest during Phase 1. `projectPath` is stored **absolute** in `manifest.json` (the analyzer/resume need it locally) but emitted on the uploaded node **relative to the graph's `scanPath`** (e.g. `frontend/acme-site`), so the graph is portable across machines/users — a consumer rebinds their own local root (`abs = join(localScanPath, projectPath)`). The relativization happens at transform time via the shared `relativeToBase` (`mcp/src/transform/relativePath.js`), which falls back to the absolute path when there is no base (offline) or the project is not under it. `repoUrl` is likewise normalized at transform time (`normalizeRepoUrl` in `mcp/src/transform/repoUrl.js`) to a canonical browser HTTPS URL with no `.git` suffix (SSH scp-style `git@host:org/repo.git`, `ssh://`, `git://`, and `https://` remotes all collapse to `https://host/org/repo`); unparseable values pass through untouched. Node `data` on the backend is one **flat five-field schema** shared by every node type — `engine`, `port`, `hostname`, `technologies`, `packageName`, all nullable, no per-type validation, keys outside the five are not persisted; the transform still emits a per-type subset: engine-backed nodes (`database` / `cache` / `queue` / `storage` / `search` / `realtime`) send `engine` (`null` when unknown — never a fabricated value) and `port` as `int|null`; hostname-backed resource nodes (`gateway`, `monitoring`, `auth_provider`, `cdn`, `external_api`, `other`) send `hostname`. A scanned project maps to a `project` node (client app) unless its `project.md` declares `role: service` (→ `service` node carrying `port`), `role: library` (→ `library` node carrying `packageName`, no port), or `role: admin_panel` (→ `admin_panel` node carrying `technologies` like any other project node) (`mapRoleToType` in `mcp/src/transform/kinds.js`) — this affects the node's `type`, its key in edge wiring, and its deterministic id, so the reader, `nodes`, `edges`, and `write_node_manifests` all resolve a project's type the same way. Because ids are deterministic over `(graphId, type, name)`, reclassifying an existing resource (e.g. a Redis node moving `database` → `cache`) mints a new UUID on the next scan — the old node is replaced and its saved position/links are lost; this is expected. The payload also carries a graph-level scan-owned `scanPath` (the root `scan_dir`) and the graph-owned `agentContext`. `scanPath` is emitted **relative to `$HOME`** (e.g. `Projects/acme`) using the **same** `relativeToBase` resolver as `projectPath` (just anchored at home instead of the scan root), so the shared graph doesn't leak an absolute machine path; it falls back to the absolute path when the scan root is not under home. It's informational metadata only — `plan_clone` ignores it and re-bases the relative `projectPath` onto a user-supplied `base_dir`. `bind_context` resolves a working copy (raw git remote URL + target dir + base_dir) to its graph node — cache lookup with validation/repair, fallback search across all graphs, returning the bound node, its edges, and neighbor availability; it owns `~/.quasar-graph/cache/bindings.json`.

# Architecture

The scanner runs in these phases, all inside the `scan` skill:

0. **Phase 0 — Backend binding** (`scan` orchestrator, main thread, via the bundled MCP server). Picks the target backend project (`list_projects`, with a `Create new project` option backed by `create_project` — the fallthrough when the list is empty) and then **new or existing graph**: existing → `list_graphs project_id` + `pull_graph` (downloads `<session_dir>/graph/graph.json` — the full snapshot; no per-node buffer files); new → `create_graph`. Records `{project_id, project_name, graph_id, graph_name, mode}` in a top-level `backend` block in `manifest.json`. The graph is always the **logical + ingress overlay** model: dependency edges plus the gateway/ingress routing path as a separate `routes` edge class. The overlay is purely additive — it never removes or rewrites a logical edge — and there is no toggle for it. If the MCP server is unavailable, this phase is skipped (**offline mode**): the scan still runs and writes to disk, and Phase 4 is skipped.

1. **Phase 1 — Catalog** (`scan` orchestrator, main thread). Globs marker files (`package.json`, `pyproject.toml`, `go.mod`, `pubspec.yaml`, `docker-compose.yml`, …) under `scan_dir` at depth 1–3, skipping a blacklist (`node_modules`, `.venv`, `dist`, `.quasar-graph`, …). Writes the manifest to `<cwd>/.quasar-graph/<session_id>/manifest.json` (output lives under the current working directory, NOT inside `scan_dir`) with each project as `status: pending`. Ends with a **deep-scan approval gate**: Phase 2 starts only after the user explicitly approves the cataloged list (projects **and** environments) — the user adjusts exclusions over as many rounds as needed first; excluded entries get `status: skipped` in the manifest and are never analyzed, never produce a node/`.md`, and are not flagged by the Phase 3.5 "missing project" check.

2. **Phase 2 — Deep analysis** (`scan` dispatches general-purpose sub-agents in **batches of 3**). Each sub-agent loads `analyze-project` and receives `project_name`, `project_path`, `session_dir`, and the **full `manifest.json` content** in its prompt (so it can resolve cross-project links). The sub-agent reads only whitelisted config files (manifests, `.env*`, `docker-compose*.yml`, ORM configs, root `README.md`) — **never source code**. It writes `<session_dir>/scan/projects/<name>/<name>.md`. The orchestrator (not the sub-agent) flips `status` to `done` in the manifest.

3. **Phase 3 — Aggregate resources** (`scan` orchestrator, main thread, **not via sub-agents**). Reads every `scan/projects/*/<name>.md`, parses its `resources:` block, dedupes by `host_key` (bare hostname / `<type>-<id>`), classifies each group as **self-hosted** (`.local`, `localhost`, private IP, no TLD, or matches a compose service in any scanned project) vs **third-party** (default when ambiguous), and writes one file per resource into `<session_dir>/scan/resources/<slug>/<slug>.md` or `<session_dir>/scan/third-party/<slug>/<slug>.md`. `connections:` entries are NOT resources and are skipped. At the tail of Phase 3, the orchestrator calls `write_node_manifests` (`session_dir`) — it reads `graph/graph.json` + the `scan/` folders and writes a per-node `manifest.json` (`{ id, position, agentContext }`) beside each `.md`. Existing/edited positions and `agentContext` are preserved (idempotent — an on-disk edit wins over the snapshot). In offline mode it still runs and writes `{ id }` only. Then the orchestrator calls `build_graph` (`session_dir`), which assembles the full snapshot and overwrites `graph/graph.json` — the artifact Phase 3.5 reviews and Phase 4 uploads.

4. **Phase 3.5 — Pre-upload review** (`scan` dispatches **one read-only** `general-purpose` sub-agent). It reads the whole assembled session (manifest, all `scan/projects/*`, `scan/resources/*`, `scan/third-party/*`, and `graph/graph.json` if present) and reports likely mistakes that only emerge once the graph is whole — reciprocal/wrong-direction connections, dangling/self-loop connections, a peer project filed as a resource, resources without consumers, duplicate or over-merged resources, self-hosted/third-party misclassification, orphan nodes. The review is **advisory**: it never edits files and never blocks. The orchestrator presents findings and **waits for the user** to choose fix-first or upload-as-is.

5. **Phase 4 — Upload to backend** (`scan` orchestrator, main thread, via the bundled MCP server). The target was chosen in Phase 0 and the snapshot was assembled by `build_graph` in Phase 3, so after the user confirms the review the orchestrator just calls `push_graph` (`session_dir`), which validates `graph/graph.json`, recomputes deterministic ids, and POSTs to `/scan` — the backend **fully replaces** that project's graph. Graph-owned per-node fields (`position`, `agentContext`) materialized in Phase 3 **are preserved** across re-scans; scan-owned fields (`description`, `projectPath`, `repoUrl`, and the graph-level `scanPath`) are refreshed every time, except that a node value the fresh scan could not produce is backfilled from the previous snapshot (fill-missing). In offline mode (no `backend` block) this phase is skipped and the on-disk output is still complete.

**Resume semantics:** the session is chosen at the very start, in a **Session step** that precedes Phase 0: `list_sessions` (local, read-only, no auth — `mcp/src/tools/listSessions.js`) summarizes every `<cwd>/.quasar-graph/*/manifest.json` newest-first with its bound graph, `scan_dir` and `done`/`pending`/`skipped` counts, and the user picks `New session` or one of them in a single selection (no sessions → a new `session_id` is generated silently; an explicit `session_id` in the invocation skips the prompt). Directories without a readable `manifest.json` — `/quasar-graph:edit` sessions, aborted runs — are not scan sessions and are only counted as `skipped_dirs`. The choice decides `session_dir` and nothing else: what actually gets skipped still follows from the manifest's contents — if `<session_dir>/manifest.json` already exists, Phase 1 is skipped entirely (including the approval gate); Phase 2 processes only `pending` entries (`projects` **and** `environments`) — `skipped` entries stay skipped until manually edited back to `pending`. Same `session_id` = resume; new `session_id` = full re-scan.

# Output layout

```
<cwd>/.quasar-graph/<session_id>/   # cwd = where the scan is invoked, not scan_dir
  manifest.json                     # session control + backend binding
  graph/graph.json                  # downloaded snapshot (existing-graph mode)
  scan/
    projects/<name>/<name>.md       # one per scanned project
    projects/<name>/manifest.json   # graph-owned { id, position, agentContext }
    environments/<name>/<name>.md   # deployment/infra source (NOT a node) — resources + topology only
    resources/<slug>/<slug>.md      # self-hosted resources (Phase 3)
    resources/<slug>/manifest.json
    third-party/<slug>/<slug>.md    # SaaS / external (Phase 3)
    third-party/<slug>/manifest.json
```

**Environments vs projects:** a scanned directory is classified in Phase 1 as a `project` (→ `manifest.projects[]`, becomes a `project`/`service` node) or an `environment` (→ `manifest.environments[]`, a deployment/infra descriptor like a `devops/` compose tree). An environment is analyzed for its `resources[]` (including the `kind: gateway` edge layer — Traefik/nginx) and deployment topology, but produces **no node and no edges from itself**: its resources fold into Phase 3 aggregation (with `hosted_in`, never as a `consumer`), and its topology folds into the graph-level `agentContext`. Resources only an environment surfaces (Traefik, monitoring) are legitimate consumer-less self-hosted nodes.

`<session_id>` format: `YYYYMMDD-HHMM-<6-hex>` (e.g., `20260519-1430-a3f2c1`).

# Source of truth: `project.md` frontmatter

The YAML frontmatter is the machine-readable core of the graph; the markdown body is for humans. Schema (omit absent fields rather than emitting empty arrays):

- `name`, `language`, `framework`
- `role` — optional; `service` marks a backend service (→ `service` node carrying `port`), `library` marks a shared package/SDK (→ `library` node carrying `packageName`), `admin_panel` marks an administration/back-office UI (→ `admin_panel` node), otherwise omit and the project becomes a client `project` node. `port` — optional int, only meaningful with `role: service`. `package_name` — optional registry name (`@scope/name`, `vendor/name`), only meaningful with `role: library`
- `resources[]` with `kind` (`database` / `cache` / `queue` / `storage` / `external_service` / `auth_provider` / `monitoring` / `cdn` / `search` / `realtime` / `gateway`), `type`, `env`, optional `name`/`admin_url`/`description`. Each kind maps to its own node type via `mapKindToType`, except `external_service`, which maps to `external_api`, and unknown kinds, which map to `other`. `gateway` is the edge/infra layer (reverse proxy, ingress, API gateway, web server — Traefik, nginx, …)
- `env[]` — every env var name seen across `.env*` (names only, never values)
- `connections[]` with `project` (must match a peer's `name` in `manifest.json`) and `via` (`rest_api` / `grpc` / `shared_database` / `message_queue` / `webhook` / `file_share` / `client_of`)

Body requires a `# <name>` heading + 1–3 sentence description, and a `## Resources` section bulleted from `resources[]` (omit the section if `resources: []`).
